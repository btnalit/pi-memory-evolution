## F3 — whole-window ceilings and byte-as-token context arithmetic

- **Commit:** `5dae138`
- **What changed:** `answerCeiling(modelMaxTokens, contextWindow)` in `src/memory/limits.ts`
  returns `undefined` when the ceiling is no smaller than the window — the catalog's convention
  for "may use the whole window" — so nothing is sent and `MAX_OUTPUT_TOKENS` is reserved, exactly
  as for a model declaring no limit; both call sites (`src/adapter/pi-api.ts`,
  `src/memory/evolution.ts`) pass the window, so the number sent and the number reserved stay one
  value. A new `estimateTokens()` (one token per CJK code point, at most three bytes per token
  elsewhere) replaces byte counting in the context arithmetic, with a 400-token slack term
  (`CONTEXT_SLACK_TOKENS` in `evolution.ts`) in place of the old 1,200 bytes. `docs/design.md` and
  `docs/recovery.md` describe both.
- **How verified:** probe with the review's own model shape,
  `{provider: 'mistral', id: 'devstral-latest', contextWindow: 262144, maxTokens: 262144}`, through
  the real `evolve()` with a counting `complete` stub: `evolve returned true | provider called
  1 times | reserved outputTokens=12800`; status `done=1`, no `context_limit`. Before the fix the
  review's same probe printed `context_limit | provider called 0 times`. `answerCeiling` on
  `(262144, 262144)`, `(300000, 262144)` → `undefined`; on `(4096, 128000)`, `(4096, undefined)`,
  `(4096, 0)`, `(4096, NaN)` → `4096`. `estimateTokens('😀')` is 2 (one astral code point, four
  bytes, never split), `'𠀀'` (astral Han) is 1. Regression tests: `src/memory/evolution.test.ts`
  "a model declaring its whole window as its ceiling is treated as declaring none, and is actually
  called" and "context arithmetic counts tokens, not bytes, so a payload that fits is not refused
  unsent"; `src/adapter/pi-api.test.ts` gained whole-window / over-window / within-window rows.
  Break-the-fix: removing the `>= contextWindow` early return in `answerCeiling` turns the
  whole-window test and the `pi-api` ceiling table red; restoring `Buffer.byteLength` and the
  1,200-byte slack in `evolution.ts` turns the tokens-not-bytes test red. The pre-existing
  `ctx(19000, 20000) → context_limit` case still discriminates: the evaluated system prompt, as the
  adapter receives it, is 4,445 bytes ≈ 1,482 tokens, so 20,000 − 19,000 − 1,482 − 400 = −882.
- **Left out:** the cost-side `promptBytes: … + 1200` term feeding `estimatedCost()` is unchanged
  — it is the spend estimate, meant to stay conservative, and the finding scopes to context
  arithmetic. No test walks Pi's catalog for the 182 entries; the fixture uses the review's own
  `mistral/devstral-latest` shape. `estimateTokens()` walks the text character by character with
  a regex test, and the candidate-pop loop in `evolve()` calls it once per popped candidate:

## F2 — any event in a scope invalidated every in-flight result

- **Commit:** `6098949`
- **What changed:** `generation()` counts only events whose `after` is non-empty, through the
  exported `CHANGED_EVENT_SQL` (`json_array_length(json_extract(data,'$.after'))>0`), and the
  constructor creates the partial index `events_scope_changes ON events(scope) WHERE …` on the
  same expression; no schema bump (`CREATE INDEX IF NOT EXISTS`, like the other indexes; status
  still prints `schema 7`). The call-budget charge for a stale result is **kept and documented**
  in `docs/recovery.md` (call *and* failure budget with backoff): the request was sent and may
  have been billed, and `calls` is seeded from `COUNT(*) FROM model_calls` on the v6 upgrade
  (`memory-store.ts:154-155`), so reversing the charge would make the two disagree.
- **How verified:** by reading every write path: `record()` is the only writer of the `memories`
  table and always puts the rows it wrote in `after`; `capture()`, `finishEvolution()`,
  `feedback()`, `act()` (forget, pin, unpin, resolve, conflict, adopt), `undo()` and the legacy
  import all go through it, `undo()` refuses an event with no `after`, and `block()` — the only
  other writer of `blocked` — is only ever followed by a `record()` with a non-empty `after` in
  the same transaction. So "an event with a non-empty `after`" and "a memory row changed" are
  the same set. Probe through the real `evolve()`: with a zero-claim user capture and a
  no-change model reply for another source landing while the call is in flight, `evolve
  returned true` (before the fix: `stale`, `failures=1`, `calls=1/4`); with a pin and unpin in
  flight instead, `stale` — a pin writes the record, and the charge shows as documented
  (`s1: stale … calls=1/4`). Regression test: `src/memory/memory-store.test.ts` "an event that
  changed no memory does not invalidate an in-flight result; one that did still does", with a
  positive control (a summary capture with a new local claim still yields `stale`) and an
  `EXPLAIN QUERY PLAN` assertion that the exact query uses `events_scope_changes`.
  Break-the-fix: dropping the `AND ${CHANGED_EVENT_SQL}` clause from `generation()` alone
  turns that test red. Timing, re-measured over 200,000 events in one scope (one in fifty
  changed): 0.017 ms per query with the partial index (`SEARCH events USING INDEX
  events_scope_changes`), 0.089 ms without it (`USING INDEX events_scope`).
- **Follow-up, `a18c426` — a defect the fix introduced:** the independent review of this commit
  found that narrowing the generation reopened a race the full review's "Concurrency" section had
  probed and ruled out. A confirmation (`reinforce()`, which stamps `reinforcedAt`) writes no
  event at all — it is "not a change" by design — and had been protected only because
  `finishEvolution`'s always-written event, empty or not, made a competing in-flight result
  `stale`. After `6098949`: S1 confirms record E and finishes first with no content change; S2,
  captured *earlier* than S1 but finishing after it, replaces another record with text equal to E
  and so writes E through from its older snapshot (`finishEvolution`'s `existing` branch). S2 is
  not stale — nothing it was shown changed — and commits; E's `reinforcedAt` from S1 was gone and
  its decay anchor (`max(updatedAt, reinforcedAt)`, `quality.ts`) went from 09-06 back to 09-04,
  with no error and no diagnostic. Reproduced in this session with a two-run probe (`S2 threw?
  false; EXISTING.reinforcedAt=undefined`). The fix: `record()` carries the current `reinforcedAt`
  onto every write when it is newer than the one being written — for every writer, exactly the
  rule `undo()` already applied — so the result still commits (no paid call is wasted on a mere
  confirmation) and the stamp survives. `docs/design.md`'s confirmation paragraph and the
  `reinforce()` comment say so. Regression test: `src/memory/memory-store.test.ts` "a write-through
  from an older snapshot cannot erase a confirmation stamp written meanwhile" — red before the
  fix on exactly the stamp assertion (`actual: undefined`), green after; disabling the carry-forward
  map turns only that test red. The other ordering (S2 newer than S1) was never harmful: the
  write-through's own `updatedAt` moves the anchor past the lost stamp. Nothing else a
  confirm-only finish writes can be clobbered — `reinforce()` touches only `reinforcedAt`, and any
  other change goes through `record()` with a non-empty `after`, which does move the generation.
- **Left out:** feedback and pins still move the generation, deliberately: they write the record
  (a verdict or layer plus a revision), and an in-flight reply must not overwrite a record the
  user just marked incorrect. The stricter alternative the review mentions — snapshotting
  `(id, revision)` of `run.memories` — was not taken; with the carry-forward it is not needed for
  the stamp, and it would make a mere confirmation waste the paid call the fix set out to keep.

## F6 — `DIRECTIVE` turned one-off sentences into paid learning calls

- **Commit:** `48371e6`
- **What changed:** `src/memory/learning.ts` gains a `directive()` helper used in all three
  places `DIRECTIVE.test()` was: (1) a text ending in `?` or `？` is never a directive, so no cue
  overrides the recall-question or question gates for it; (2) a bare imperative
  (`always`/`never`/`don't`/`do not`) followed in its own sentence by `for now`, `for this`,
  `this time`, `just` or `yet` does not count. The explicit openers (`from now on`,
  `going forward`, `in (the) future`) are exempt from (2): they say in their own words that the
  rule is durable, and there "just" means "only" — so `From now on, just run the unit tests.` is
  still learned. The `DIRECTIVE` literal is byte-for-byte unchanged, so the doc-constants walk of
  its shape holds; the global copy is built from `.source`/`.flags`. `docs/usage.md` documents
  both narrowings next to the cue list.
- **How verified:** probe with `learningIntent()` over the eleven negatives the finding and the
  test name (the five sentences quoted in the finding, one per one-off marker, and `?`-ending
  sentences opened by durable openers): all `learn: false`; over seven positives including the
  pre-existing cues and the two durable-opener fixtures: all `learn: true`; zero mismatches.
  Regression test: `src/adapter/progress-pipeline.test.ts` "one-off instructions and questions
  that merely open with a directive word are not learned" (14 sentences) plus two positive
  fixtures pinning the durable-opener decision. Break-the-fix: making `directive()` return
  `DIRECTIVE.test(text)` turns that test red on its first sentence. `test:pi` passes with its
  request counts unchanged, so no session-level fixture turned into a learning call.
- **Left out:** the Chinese cues (`以后`/`不要`) go through `IMPERATIVE`, not `DIRECTIVE`, and
  still override the question gate — `以后不要用 sed 吗？` is learned (probed). That is
  pre-existing and outside the finding. Two edges of the new rule, probed and accepted: a rule
  followed by a confirmation question in the same text, `Always run the tests. Is that ok?`, is
  not learned, because the trailing `?` is tested on the whole text — the finding's own negative
  `Always the same stack trace when I run it. Why?` needs exactly that, since its cue sentence
  ends in a full stop, and the recognizer's "a stated preference may precede a question" is
  served by the stated-requirement paths, which are untouched; and a marker in the *next*
  sentence does not cancel a cue (`Never use sed here. Just edit the file.` is learned).
  `Don't just run the tests, tell me what failed.` is not learned; that direction (missing a
  rule rather than inventing one) is the one the recognizer already errs in, and
  `remember`/`prefer` still work for it.

## F7 — a generic model-written alias counted as naming the topic

- **Commit:** `f2fb900`
- **What changed:** `src/memory/retriever.ts` keeps the per-word document frequency it already
  computes for the weights (`frequency`) and counts an alias or concept toward `topicMatches`
  only when `df <= max(2, 0.02 * documents.length)` — the floor is 3 since the follow-up below;

  remain. `docs/usage.md`,
  `docs/design.md` and the `MIN_FOCUS_COVERAGE` comment in `limits.ts` state the rarity clause.
- **How verified:** probe with the review's badge note (aliases `['server', 'access']`) beside
  its alias-less twin on the review's prompt, in stores of different sizes. Regression test:
  `src/memory/conversation-recall.test.ts` "an everyday alias shared across the store does not
  name a topic; a rare one still does" — a 17-record store in which `server` has df 5 against a
  threshold of `max(2, 0.34) = 2` (3 since the follow-up; df 5 clears both); both twins must be
  `incidental-overlap`. Before the fix the
  aliased note was `selected` on `server,needs` while the twin was `incidental-overlap`, exactly
  the review's diagnostics. Positive controls in the same test: the drill's rare-alias `indent`
  case still recalls, a rare concept (`concept:database` in the `project` fixture) still carries
  `staging`, and a concept shared by six port records does not carry an unrelated one; the six
  existing clutter fixtures remain the guard against bare prose words counting. Break-the-fix:
  making `rare()` return `true` turns the twin test red.
- **Follow-up, `eea46b3` — a cost of the prescribed formula, measured and corrected:** the
  formula is the review's own (`df <= max(2, 0.02 × records)`), and verifying it against the
  drill's headline case — a long task prompt naming a topic — found that the floor of 2 silenced
  a real topic as soon as three records carried it, in any store under 150 records. Probed on a
  14-record store with three records aliased `billing` (a decision, a retry policy, a tax rule)
  and a three-line task prompt about the billing service: `df(billing) = 3 > 2`, so none of the
  three was carried on the subject side, all three were `incidental-overlap`, and nothing was
  injected — where with one or two billing records the decision was selected, and where before
  `f2fb900` it was too. A topic with several records is the ordinary shape of a project store,
  and that prompt is exactly the case the drill (`8127577`–`297e9c3`) set out to serve. No
  monotone threshold on document frequency can both reject `server` at df 2 of 7 (the finding's
  small-store case, below) and accept `billing` at df 3 of 14 — the two are separated by
  vocabulary, not counts — so the floor was set where the rule's two costs meet: 3. A topic keeps
  naming its records while up to three carry it (more as the store grows past 150), and an
  everyday alias is held out from df 4; the twin fixture sits at df 5 and passes unchanged.
  `docs/design.md` states the floor and why. Regression test:
  `src/memory/conversation-recall.test.ts` "a topic carried by three records still names them on
  a long task prompt" — the billing case (red before the fix: all three `incidental-overlap`,
  green after), the same prompt with nothing about billing stored still injecting nothing, and an
  everyday alias shared by four records still held out. Setting the floor back to 2 turns only
  that test red. Re-probed after the change: the badge twins are held out from df 4 (they were
  from df 3), and at df 5 — the fixture — as before.
- **Left out — the limit that remains, stated plainly:** the floor does not fix the finding's
  own small-store case, under either value. In a 7-record store where `server` occurs only in
  the two twins (df 2) the aliased note is **still selected**, and it stays selected until a
  fourth record mentions servers (df 4; under the original floor, a third). The review's probe
  was "a 7-record store"; if `server` had df 2 there, neither floor changes that probe's outcome.
  In a store where only one note talks about servers, "server" is that note's topic by the data
  — no data-driven rule can tell it from a real topic there, and a vocabulary list of everyday
  words is the prompt-dependent rule `b0a07db` deliberately moved away from. This was left as
  the documented boundary of the rule rather than re-opened.
